# PostgreSQL DDL implementation plan v0.1

**Owner:** #46  
**Approved design input:** #45.

## Migration order
1. `meta` and `ref` schemas/tables.
2. `core` typed entities.
3. `assessment`.
4. `treatment`.
5. `enterprise`.
6. `governance`.
7. `pharma`.
8. views/derived relations.
9. indexes/checks/exclusion constraints.
10. seed/reference vocabularies and negative-integrity fixtures.

## PostgreSQL choices
- UUID primary keys; generated by DB/application under one frozen convention in #46.
- `timestamptz` for occurrence/validity timestamps.
- `tstzrange` may be used for validity intervals where it simplifies non-overlap constraints.
- explicit schemas, never `public` for evaluated domain tables.
- snake_case physical names; semantic IDs stored in mapping/metadata, not encoded into opaque column names.
- controlled codes use reference/check tables where stable; free-text source values remain traceable in staging.
- JSONB is permitted only for provenance/tool metadata not required for semantic parity; no release-critical semantic field may exist only inside JSONB.

## Required implementation checks
- clean DDL succeeds on supported PostgreSQL version;
- every FK/check/unique/exclusion rule in #45 catalog exists or has a documented deviation;
- ontology↔RDB mappings resolve to implemented tables/columns/views;
- `v_risk_owner` is derived from responsibility assignments;
- no `risk.owner_id`, no conflated risk/workflow state, no duplicate inherent/residual Risk rows;
- negative inserts fail for all release-critical integrity rules;
- exact schema can be recreated without manual edits.

## Migration policy
Any semantic mapping change after evaluated runs requires a new migration and mapping version; edited historical migrations are prohibited.
